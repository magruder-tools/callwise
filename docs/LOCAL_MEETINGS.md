# Local meeting implementation

Callwise 0.5 keeps the existing Electron app, secure preload, capture worklet, coaching engine and source-validation code. The notebook is the primary surface; the coach panel is optional. A single SwiftPM executable is packaged in `Contents/MacOS/callwise-native`; Core ML model resources and the fixed Notes JXA script live in `Contents/Resources/native`.

The native helper supports capabilities, assets, speech, diarize, llm, reminders and calendar modes over bounded JSON lines. Processes have fixed arguments, a minimal environment and no shell. Standard output is the protocol; arbitrary upstream stderr is never forwarded. The speech process owns independent microphone and remote-channel analyzers. Sample clocks assign exact 24 kHz packet positions. Resampling disables priming; only the first/discontinuous converted buffer receives an explicit timestamp, avoiding overlap errors. Pause/End drain final words with generation guards; an unfinished partial retains its ID and is marked unfinalized after the deadline. Recovery is limited and reports gaps.

MeetingService coordinates encrypted records, canonical transcript/notes, user corrections, recaps/actions, export journals and background work. SQLite uses WAL and AES-256-GCM records bound to table/meeting/record IDs. The schema stores generic sealed records per record type rather than duplicating document contents into specialized SQL columns. Search and MP3 encoding run in workers. The live renderer reuses transcript deltas; decrypted working sets are bounded. Expensive passphrase backup work runs in a worker. Pending full-disk writes remain in a bounded memory retry buffer with a visible warning.

Original notes have version guards and timestamped lines. Enhanced notes are separate and never replace original notes. Local generation uses bounded chunks, runtime structured schemas and citation validation. Owner/date suggestions require exact supporting quotes and explicit review. Recap or note edits cause late regeneration to become a draft. Action IDs and user edits/dismissals are retained across regeneration. Background completion for a previous meeting has independent audio/speaker consumers and survives starting another meeting; queued recap/enhancement work is recoverable.

FluidAudio is locked to v0.12.4 by SwiftPM and Package.resolved. Direct Core ML model construction bypasses FluidAudio download APIs. Supported Community-1 files are pinned at Hugging Face revision `7eab74f3463c736418d0eb10296261ae581146c9`, with per-file size/SHA verification. Temporary cluster IDs are mapped to stable meeting-scoped speakers using time overlap. Manual names/assignments win. Speaker processing is scheduled at 3, 8, 15, 25, 40, 60 and 90 minutes and at the end; slow provisional runs switch to final-only processing.

Apple follow-through is deliberately separate from read-only meeting MCP. Reminders uses EventKit with stable markers. Notes uses a fixed JXA file with JSON arguments and escaped content. Export previews are fingerprinted; changed content requires a fresh preview. Pending/done/failed journals and destination marker lookups prevent retries from creating duplicates.

`--mcp-server` runs before window creation and the single-instance lock. It preserves the app's original userData for archive/key access, isolates its Chromium session directory, opens the store read-only, and rechecks the access switch on each request. It supports MCP 2026-07-28 stateless metadata/discovery and the 2025-11-25, 2025-06-18 and 2025-03-26 initialize handshakes. Assistant setup previews the exact own-entry addition, checks that the configuration has not changed, and creates a backup. It never rewrites personal_mac.

Implementation adjustments to Claude's plan were evidence-driven: FluidAudio v0.12.4 has no NemoTextProcessing binary dependency; the tested SDK makes resource-limit override available on macOS 27; runtime GenerationSchema avoids a missing FoundationModels macro plugin; speech processes are recreated on resume to make capture epochs independent; the archive's sealed-record schema retains the same content and authenticated boundaries with fewer plaintext columns. Changing capture/cloud/language settings requires a fresh meeting/notice rather than changing an active meeting's receipt.
